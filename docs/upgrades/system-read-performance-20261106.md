# 任務、UOF 與會議第二輪讀取改善

第一輪正式量測顯示會議清單較快，但任務與會議內容仍等數秒，UOF 在登入接續與案件數不同的條件下甚至較慢。本輪繼續處理可驗證的重複與串行讀取；不把傳輸量減少視為等待時間已改善。

DailyLog 保留完整清單與原本的最新權限核對，省去 GET 清單沒有使用到的兩次主管狀態查詢；明細及選人清單省去一次。內部精確 Request 可取得輕量身分，公開登入仍完整回覆。只有最後回應仍為 204 才採用內部結果，後續 wrapper 的拒絕或不同身分回覆優先，沒有捕捉資料的 204 必須拒絕。首次登記、集中人員名單同步、撤權與回傳前核權不變。

UOF 僅在 GET pending、web-pending、bootstrap 同時讀取互相獨立的留言及文件補充資料；文件明細與主旨仍保持先後。最多兩條讀取，原每批 40／10 上限、帳號與站點核對、重試及錯誤順序保持。綁定檢查前後的兩次 SSO 都重新核對，原簽核提交與背景呼叫保持原流程。固定名稱的 Server-Timing 記錄分段，不包含人名、帳號、網址或秘密；巢狀分段不能相加。

會議同一次讀取驗證共用同一身分，後續語系、任務進度及下一次請求仍重新查核。獨立查詢並行；LINE 成員必須在身分完成後查詢，服務目的地必須在主持人與觀看者核對後讀取。詳見 [會議測試](meeting-read-latency-20261106.md)。

## 隔離驗證

- DailyLog：12 個可攜測試、43 次完整 Worker 回覆逐位元對照、6 個集中名單情境、10 個原寫入權限情境及 11 個祖先分享情境。
- UOF：12 個可攜測試、10 個完整 Worker 新情境、9 個原完整 Worker 情境及 138 個原回歸測試。
- AM：原 27 組會議回歸、24 項任務串接，以及新完整 PostgreSQL 路由、途中撤權、退群及服務目的地變動測試。
- 任務每次主管查詢固定加入 120 ms 延遲，五次中位 329→62 ms；沒有人工延遲的大清單兩輪為 568→632 ms、467→459 ms，不能稱穩定加速。
- UOF 每次補讀固定加入 80 ms，三次中位 281→190 ms。
- 會議每次遠端讀取固定加入 80 ms，主持人完整讀取平均 1,410→658 ms、一般成員 1,204→660 ms；外呼 14／12→10。此比例不能套用正式速度。
